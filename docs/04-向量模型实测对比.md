# 向量模型实测对比

> 样本：1,200 条真实帖子（价值分 ≥ 5、已去重的代表条目），正文截断 512 字。
> 同一样本集、同一批查询，两边各自算余弦取 Top-K。

## 速度与成本

| | 本机 `bge-small-zh-v1.5` | 模力方舟 `bge-m3` |
|---|---|---|
| 维度 / 13.2 万条存储 | 512 维 / **65 MB** | 1024 维 / 129 MB |
| 单条耗时（实测） | **44 ms** | 67 ms（对照测试）→ **486 ms（持续跑）** |
| 全量预计 | **97 分钟** | 147 分钟 → 实际不可用 |
| 批次 | 32 稳定 | 32 会超时，**必须降到 16** |
| 持续可靠性 | 1200/1200，零失败 | 跑 384 条即超时中止 |
| 费用 | 0（本机 CPU） | 模型标价免费，但需账户有计费资源 |

### 关键结论：方舟不适合跑批量

对照测试（1200 条、批次 16）里方舟一切正常、67ms/条；
但**改成持续跑全量后，速度掉到 486ms/条，并在 384 条时超时中止** —— 被限流了。
批量任务（十几万次调用）和交互式查询（每次几次调用）是完全不同的负载。

## 检索质量

**各有胜负，总体打平。** Top-10 重合度只有 1~6/10 —— 两个模型找到的东西确实不一样。

| 查询 | 更准的一方 | 说明 |
|---|---|---|
| 不用信用卡就能注册的国外服务 | **本机** | 命中「Manus 无需绑卡」「无卡订阅 Gemini」「gopay 印尼号注册」 |
| 学生党怎么省钱买软件 | **方舟** | 命中「微软学生 365」「WorkBuddy 学生认证」「.edu 临时邮箱」 |
| 怎么白嫖服务器 | 方舟略好 | 覆盖面更广（白嫖 plus / 图生图 / 机场列表） |
| 有没有便宜的国外主机 | 平手 | 两边都是真 VPS 优惠 |
| AI 写代码哪个好用 | 平手 | 结果高度重叠 |

## 复测：全部完成后重新验证方舟是否可用于批量（重要修正）

系统全部跑通后，用充值后的账户、以 16 条/批持续压测 400 条（失败自动重试 3 次）：

```
第  1 批:  6294ms   393ms/条
第  2 批:   441ms    28ms/条   ← 快的时候确实很快
第  3 批:   559ms    35ms/条
第  4 批: 45943ms  2871ms/条   ← 突然卡住 46 秒
第  5 批:   607ms    38ms/条
第 10 批:   636ms    40ms/条
第 15 批:   489ms    31ms/条
第 20 批:   500ms    31ms/条
第 25 批:   736ms    46ms/条
```

**0 批硬失败，但有严重的间歇性停顿。**

这修正了之前的说法。早先记为「持续跑会掉到 486ms/条并被限流」，
更准确的描述是：**它不是稳定地慢，而是大部分时候很快（28~46ms/条）、
偶尔毫无征兆地卡住几十秒**（第 4 批 46 秒）。

| | 本机 | 方舟 |
|---|---|---|
| 单条耗时 | **稳定 44ms** | 28~46ms，但夹杂 2871ms 的尖峰 |
| 全量 13.2 万条预计 | **97 分钟** | **1112 分钟（18.5 小时）** |
| 耗时可预测性 | 高（速率平稳） | 低（最慢批次是最快批次的 100 倍）|
| 网络依赖 | **无** | 依赖代理，实测多次 ECONNRESET / fetch failed |
| 批量失败 | 0 | 0（但需重试兜底）|

结论不变，但理由更硬：**方舟的均值不差，差在长尾不可控。**
批量任务最怕的正是这个 —— 你没法估计还要多久，也没法在卡住时做别的事。
另外它依赖网络，而实测代理会不定期抖动（本项目已多次遇到）。

## 最终选型

**向量化用本机，重排用方舟** —— 两者强项正好互补：

| 环节 | 选谁 | 理由 |
|---|---|---|
| 向量化（13.2 万条批量） | **本机** `Xenova/bge-small-zh-v1.5` | 44ms/条、97 分钟、不会失败、零依赖 |
| 重排（每次查询 ~20 条） | **方舟** `bge-reranker-v2-m3` | 调用量小、不怕限流，且增益最大 |

批量任务要的是**可靠与便宜**，交互式查询要的是**准**。把两件事交给不同的服务，
比强行用一个更划算。

## 过程中修正的一个错误

第一版对比脚本在某一批请求超时后直接跳过，导致 `vecs[k]` 与 `texts[k]` **错位**，
后面所有相似度都在拿错文本比对，得出了「方舟结果近乎随机」的错误结论。
改成按下标对齐存放（缺失留 null）后，结论完全不同。

教训：**做对比实验时，先确保数据对齐，再谈结论。**

## 附：全量索引完成后的端到端验证

索引构建完成：**132,176 条 · 512 维 · Xenova/bge-small-zh-v1.5 · 零失败**
（另有 87 条未入库，占 0.07%，为正文为空或无法编码的条目）

### 一、语义检索 vs 关键词检索

两者重合度极低，是**互补**而非替代关系：

| 查询 | 语义检索 | 关键词检索 | 前 5 重合 |
|---|---|---|---|
| 免费 VPS 薅羊毛 | 948ms，有结果 | 44ms，有结果 | 0/5 |
| AI 编程工具 | 286ms，有结果 | 67ms，有结果 | 0/5 |
| GitHub 开源项目副业 | 326ms，有结果 | 55ms，**结果不相关** | 0/5 |
| 云服务器优惠 | 315ms，有结果 | 42ms，有结果 | 1/5 |
| **有没有能直接变现的项目** | **286ms，找到 3 条相关** | **139ms，零结果** | 0/5 |

最有说服力的是最后一行：**关键词一条都搜不到，语义检索能找出来。**
因为用户问的是「意图」（想赚钱的项目），而不是字面词（「变现」这个词在帖子里未必出现）。
这是向量检索不可替代的地方。

结论：**关键词检索负责精确命中，语义检索负责意图召回，两者都要保留。**

### 二、重排的增益

| 查询 | 纯向量 | 含重排 | 前 5 重合 | 第 1 名变化 |
|---|---|---|---|---|
| 免费 VPS 薅羊毛 | 280ms | 784ms | **1/5** | Curosr 学生免费 → 薅 virtnet.bond 羊毛的，停手吧 |
| AI 编程工具 | 293ms | 813ms | **1/5** | VideoTuna → [问卷] AI 编程工具使用情况 |

重排**大幅改变了排序**（前 5 只重合 1 条），代价约 +500ms。

从第 1 名的变化能看出重排在做正确的事：它把**标题直接命中查询意图**的条目提上来，
而向量更偏向**整体语义氛围相似**的条目。

### 三、三项能力的分工

| 能力 | 延迟 | 适合 | 不适合 |
|---|---|---|---|
| 关键词（FTS5） | 40~140ms | 明确词、精确命中 | 意图性提问 |
| 语义（向量） | 280~950ms | 意图召回、同义表达 | 追求绝对精确 |
| 语义 + 重排 | 780~820ms | 要前几条最准 | 频繁扫描式浏览 |

## 附二：本轮修掉的两个真问题

### 1. 重排一直是失效的

Gitee 重排接口单次最多接受 **25 个文档**，而代码把全部召回（默认 60）一次发过去，
必然返回 `400 无效的参数数组长度`。失败后**静默退回纯向量结果**，
只在响应里放一个前端不显示的 `rerankError` —— 界面上看着重排开着，实际什么都没做。

修复：按服务商上限分批（可配置），逐批请求后按下标合并排序；
分批之间并行（并发上限 4）；网络层瞬时失败退避重试 2 次。
实测分批并行后 33.7s → 4.6s。

### 2. 构建索引时整个 API 被卡住

本地 ONNX 推理跑在主 Node 进程里，CPU 密集，阻塞事件循环。实测构建期间：

| 接口 | 修复前 | 修复后 |
|---|---|---|
| `/api/health` | 1000~1400ms | **2~10ms** |
| `/api/search` | 约 1417ms | **27~129ms** |

修复：把推理挪到 worker 线程（`app/server/embed-worker.mjs`），
主线程只处理 HTTP。副作用是构建本身也变快（15.8 → 18.8 条/秒）。
