## 1. 引言

### 1.1 目的
明确本项目的功能与非功能需求、边界与验收标准，作为后续**概要设计、详细设计、开发、测试**的唯一依据。

### 1.2 范围
一个**个人情报助手**：从 Telegram 公开频道、群组及任意网页采集信息，经去重、反垃圾、分类后建立索引，支持关键词与语义检索、AI 问答分析，并主动推送与本人相关的新内容。

不含：多用户、社交、内容原创发布、商业运营。

### 1.3 术语
| 术语 | 含义 |
|---|---|
| 频道 / channel | Telegram 广播式频道，有公开预览页，**可抓取** |
| 群组 / group | Telegram 讨论群，**无公开预览页**，仅能通过机器人收录 |
| 来源 / source | 一条采集入口：频道、群、网页 |
| 条目 / post | 采集到并被索引的单条内容 |
| 聚合 / cluster | 多来源的同一条内容合并为一个事件 |
| 价值分 / value | 规则计算的内容价值评分（当前 0–8） |

## 2. 项目背景与目标

### 2.1 背景
中文技术圈大量高价值信息（免费额度、开源工具、副业项目、踩坑经验）以碎片形式沉淀在 Telegram 频道中，检索困难、噪声高、时效性强。人工浏览成本高，容易漏掉关键信息。

### 2.2 问题陈述
| 编号 | 问题 | 现状 |
|---|---|---|
| P1 | 信息分散在数十个频道，无法统一检索 | 已解决 |
| P2 | 广告、黑产、重复转发占比高 | 部分解决（仅精确去重） |
| P3 | 中文短词（2 字）检索慢 | 未解决（926 ms） |
| P4 | 靠关键词搜，换个说法就找不到 | 未解决 |
| P5 | 需要主动去搜，不会主动告知新内容 | 未解决 |
| P6 | 数据管线存在两条写入路径，报告会漂移 | 未解决 |
| P7 | 零测试、零 CI，长期维护风险高 | 未解决 |
| P8 | 依赖本机开机，无法 7×24 推送 | 未解决（本人已确认要上云） |

### 2.3 产品定位
**个人情报助手** —— 从「数据库」升级为「助手」：不需要自己想关键词，系统主动告知「最近新出现的、和我有关的内容」。

### 2.4 成功标准（可度量）
| 编号 | 指标 | 目标 |
|---|---|---|
| M1 | 每日增量更新成功率 | ≥ 99% |
| M2 | 检索有效性（前 10 条中人工判定有用） | ≥ 3 条 |
| M3 | 内容发布 → 我可见（订阅场景） | ≤ 1 小时 |
| M4 | 聚合后重复内容占比 | < 5% |
| M5 | 新环境从零复现全流程 | ≤ 30 分钟 |
| M6 | 核心逻辑单元测试覆盖 | ≥ 60% |
| M7 | 服务可用性（云端常驻） | ≥ 99%（月度） |

## 3. 干系人与用户画像

| 干系人 | 关注点 |
|---|---|
| **使用者：本人（唯一）** | 快速发现有用信息与可变现机会；不要垃圾；不要维护负担 |
| 潜在协作者（GitHub 访客） | 代码可读、可测试、有文档、能本地跑起来 |
| 内容原作者 | 版权与署名（仅索引公开信息并回链原文） |

**用户画像**：具备技术能力，关注 AI 工具、开源项目、羊毛优惠与副业机会；独居使用，希望低成本、低维护、7×24 在线。

> **重要**：使用者只有一人 → **不需要多用户/权限矩阵/注册流程**。但服务暴露在公网，仍必须有**单用户认证**（见 FR-OPS-10）。

## 4. 现状分析（As-Is）

### 4.1 已实现能力
- 全量抓取 11 个公开频道，852,771 条，2018-10 ~ 2026-10
- 精确去重、规则反垃圾、10 类自动分类、规则价值打分
- SQLite FTS5 三元组索引，3 字以上查询 29 ms
- React 19 + Vite 8 + Tailwind 4 本地应用（信息流/详情/收藏/深浅主题）
- AI 检索增强问答，SSE 流式，引用可回原文
- 多 AI 服务商配置与切换、模型列表自动获取（9 预设 + 自定义中转）
- Telegram 机器人：群内命令、定时日报、群消息反向收录
- 按链接抓取：公开频道 + 任意网页，增量去重

### 4.2 已识别技术债
| 编号 | 债务 | 影响 | 优先级 |
|---|---|---|---|
| D1 | 数据双写路径（DB 与 JSONL 各自可写） | 报告静默过期 | **最高** |
| D2 | 零测试、零 CI | 回归风险不可控 | 高 |
| D3 | 2 字词走 LIKE 全表扫 | 最高频查询最慢 | 高 |
| D4 | 无近似去重 | 同一事件多频道重复 | 中 |
| D5 | 价值分为纯规则，无反馈闭环 | 排序不贴合口味 | 中 |
| D6 | 报告为静态快照 | 与实时数据不一致 | 中（D1 的子问题） |
| D7 | 仅限本机运行 | 无法 7×24 推送 | 高（已确认要上云） |

### 4.3 硬约束（不可突破）
| 编号 | 约束 | 证据 |
|---|---|---|
| C1 | **Telegram 群组消息无法公开获取** | 实测 `t.me/s/qiuyueww` 仅返回 join 页、0 条消息，仅暴露成员数；11 个可抓取来源全部为频道 |
| C2 | FTS5 三元组索引最短支持 3 字 | 2 字查询无法命中索引 |
| C3 | AI 能力依赖外部 API | 已探测本机 11434/1234/8080/8000/3000 全部无本地模型 |
| C4 | 个人使用，无多用户需求 | 需求确认 Q1 |

## 11. 需求确认结果与影响分析

### 11.1 确认结果（2026-10-09）

| 问题 | 确认结果 |
|---|---|
| Q1 使用者范围 | **仅我本人**（个人情报助手） |
| Q2 部署形态 | **云服务器常驻** |
| Q3 AI 预算 | **不设上限** |
| Q4 灰色内容 | **保留，但明确标注风险** |
| Q5 数据保留 | **全量保留** |

### 11.2 各项确认带来的设计影响

**Q1 个人使用 → 简化而非复杂化**
- ❌ 不需要：注册、登录页、多用户、角色权限、用户隔离
- ✅ 仍需要：**单用户认证**（因 Q2 服务在公网）
- 可大胆假设使用习惯：每天看 1–2 次，以移动端和 Telegram 为主入口

**Q2 云服务器常驻 → 新增一整块需求**
- FR-OPS-9 容器化部署、进程守护、崩溃自愈
- FR-OPS-10 单用户认证（否则等于把 85 万条库和 AI Key 送到公网）
- NFR-S5 强制 HTTPS
- 好处：定时抓取与日报不再依赖本机开机（解决 D7）
- 代价：需要运维、需要付费、需要处理下面 §11.3 的风险

**Q3 不设上限 → 解锁两个高价值能力**
- FR-SRCH-5 语义检索可行
  - embedding 一次性成本：只对**高分条目**（value ≥ 4，约 12 万条）做，约 3600 万 token，成本约几元
  - 存储估算：12 万 × 512 维 × 1 字节（int8 量化）≈ **60 MB**，内存完全可承受
  - 若对全部 85 万条做，float32 需约 1.7 GB，**超出 NFR-P5**，故不做全量
- FR-CLN-6 AI 辅助价值评估可行：批量给高分条目打更细的分，排序质量显著提升

**Q4 保留灰色内容 → 维持现状 + 一条新增约束**
- 继续打「风险」「破解」标签
- **新增**：自动推送（日报/订阅）默认排除「风险」标签条目，避免主动传播

**Q5 全量保留 → 容量规划**
- 年增约 15 万条 / 250 MB；考虑向量索引与备份，云端磁盘建议 ≥ 20 GB
- 检索性能不受影响（FTS5 索引增长线性）

### 11.3 ⚠️ 需要你决策的新风险

**R1（高）：云服务器 IP 可能被 Telegram 限流**

`t.me` 对数据中心 IP 常有 429/封禁策略。本机（住宅 IP）实测 56 并发稳定，但**机房 IP 未经验证**。

三种应对方案：

| 方案 | 说明 | 代价 |
|---|---|---|
| A. 抓取留在本机，云只跑应用 | 本机定时抓取 → 同步 DB 到云 | 本机仍需间歇开机 |
| B. 云端抓取 + 出口代理 | 云端通过代理访问 t.me | 需额外代理成本，且 FR-COL-9 |
| C. 云端直连，先验证 | 部署后实测并发与限流情况 | 可能失败后返工 |

**建议**：先按 C 验证一天；若被限流则退回 A（改动最小，且 A 天然规避风险）。

**R2（中）：数据同步一致性**
若采用方案 A，需要一套"本机 DB → 云端"的增量同步机制，否则又多一条双写路径（重蹈 D1 覆辙）。**这是 D1 的延伸，必须在 v0.2 一并解决。**

**R3（中）：公网暴露的合规与安全**
服务在公网且索引灰色内容，即使是个人使用，也需确保：认证不被绕过、不在公开渠道传播、Bot Token 与 AI Key 不泄露。
