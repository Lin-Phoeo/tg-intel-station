## 1. 引言

### 1.1 目的
明确本项目的功能与非功能需求、边界与验收标准，作为后续**概要设计、详细设计、开发、测试**的唯一依据。

### 1.2 范围
一个**个人情报助手**：从 Telegram 公开频道、群组及任意网页采集信息，经去重、反垃圾、分类后建立索引，支持关键词与语义检索、AI 问答分析，并主动推送与本人相关的新内容。

**仅在本机运行，不暴露公网，不提供多用户服务。**

### 1.3 术语
| 术语 | 含义 |
|---|---|
| 频道 / channel | Telegram 广播式频道，有公开预览页，**可抓取** |
| 群组 / group | Telegram 讨论群，**无公开预览页**，仅能通过机器人收录 |
| 来源 / source | 一条采集入口：频道、群、网页 |
| 条目 / post | 采集到并被索引的单条内容 |
| 聚合 / cluster | 多来源的同一条内容合并为一个事件 |
| 价值分 / value | 规则计算的内容价值评分（当前 0–8） |
| 补跑 / catch-up | 开机后检查错过的定时任务并补执行 |

## 2. 项目背景与目标

### 2.1 背景
中文技术圈大量高价值信息（免费额度、开源工具、副业项目、踩坑经验）以碎片形式沉淀在 Telegram 频道中，检索困难、噪声高、时效性强。人工浏览成本高，容易漏掉关键信息。

### 2.2 问题陈述
| 编号 | 问题 | 现状 |
|---|---|---|
| P1 | 信息分散在数十个频道，无法统一检索 | 已解决 |
| P2 | 广告、黑产、重复转发占比高 | 部分解决（仅精确去重） |
| P3 | 中文短词（2 字）检索慢 | 未解决（926 ms） |
| P4 | 靠关键词搜，换个说法就找不到 | 未解决 |
| P5 | 需要主动去搜，不会主动告知新内容 | 未解决 |
| P6 | 数据管线存在两条写入路径，报告会漂移 | 未解决 |
| P7 | 零测试、零 CI，长期维护风险高 | 未解决 |
| P8 | 本机不常开，定时抓取与推送会漏执行 | 未解决（本地部署的固有约束） |

### 2.3 产品定位
**个人情报助手** —— 从「数据库」升级为「助手」：不需要自己想关键词，系统主动告知「最近新出现的、和我有关的内容」。

### 2.4 成功标准（可度量）
| 编号 | 指标 | 目标 |
|---|---|---|
| M1 | 每次增量更新成功率 | ≥ 99% |
| M2 | 检索有效性（前 10 条中人工判定有用） | ≥ 3 条 |
| M3 | 内容发布 → 我可见（开机状态下） | ≤ 1 小时 |
| M4 | 聚合后重复内容占比 | < 5% |
| M5 | 新环境从零复现全流程 | ≤ 30 分钟 |
| M6 | 核心逻辑单元测试覆盖 | ≥ 60% |
| M7 | 错过的定时任务在开机后 | 100% 补跑 |

## 3. 干系人与用户画像

| 干系人 | 关注点 |
|---|---|
| **使用者：本人（唯一）** | 快速发现有用信息与可变现机会；不要垃圾；不要维护负担 |
| 潜在协作者（GitHub 访客） | 代码可读、可测试、有文档、能本地跑起来 |
| 内容原作者 | 版权与署名（仅索引公开信息并回链原文） |

**用户画像**：具备技术能力，关注 AI 工具、开源项目、羊毛优惠与副业机会；在个人 Windows 电脑上使用，希望零运维成本。

> **重要**：使用者只有一人，且**服务只在本机** → 不需要多用户、不需要注册、**也不需要认证**（监听 `127.0.0.1` 即天然隔离）。

## 4. 现状分析（As-Is）

### 4.1 已实现能力
- 全量抓取 11 个公开频道，852,771 条，2018-10 ~ 2026-10
- 精确去重、规则反垃圾、10 类自动分类、规则价值打分
- SQLite FTS5 三元组索引，3 字以上查询 29 ms
- React 19 + Vite 8 + Tailwind 4 本地应用（信息流/详情/收藏/深浅主题）
- AI 检索增强问答，SSE 流式，引用可回原文
- 多 AI 服务商配置与切换、模型列表自动获取（9 预设 + 自定义中转）
- Telegram 机器人：群内命令、定时日报、群消息反向收录
- 按链接抓取：公开频道 + 任意网页，增量去重

### 4.2 已识别技术债
| 编号 | 债务 | 影响 | 优先级 |
|---|---|---|---|
| D1 | 数据双写路径（DB 与 JSONL 各自可写） | 报告静默过期 | **最高** |
| D2 | 零测试、零 CI | 回归风险不可控 | 高 |
| D3 | 2 字词走 LIKE 全表扫 | 最高频查询最慢 | 高 |
| D4 | 无近似去重 | 同一事件多频道重复 | 中 |
| D5 | 价值分为纯规则，无反馈闭环 | 排序不贴合口味 | 中 |
| D6 | 报告为静态快照 | 与实时数据不一致 | 中（D1 子问题） |
| D7 | 定时任务依赖进程常驻 | 关机则漏执行，无补跑 | 高 |

### 4.3 硬约束（不可突破）
| 编号 | 约束 | 证据 |
|---|---|---|
| C1 | **Telegram 群组消息无法公开获取** | 实测 `t.me/s/qiuyueww` 仅返回 join 页、0 条消息，仅暴露成员数；11 个可抓取来源全部为频道 |
| C2 | FTS5 三元组索引最短支持 3 字 | 2 字查询无法命中索引 |
| C3 | AI 能力依赖外部 API | 已探测本机 11434/1234/8080/8000/3000 全部无本地模型 |
| C4 | **仅本机部署，不暴露公网** | 需求确认 Q2 |
| C5 | **本机不保证 7×24 开机** | 本地部署的固有约束 |

### 11.2 「本地电脑」带来的影响

**撤销的需求（原 v1.1 为云端而设）**

| 原需求 | 处理 |
|---|---|
| FR-OPS-9 云端部署（容器化/守护进程） | **删除**，替换为「可选开机自启」 |
| FR-OPS-10 单用户认证 | **删除**，改为 NFR-S5「默认只监听 127.0.0.1」 |
| NFR-S5 强制 HTTPS | **删除** |
| 风险 R1 云 IP 被 Telegram 限流 | **删除**（不存在了，住宅 IP 实测 56 并发稳定） |
| 风险 R3 公网暴露合规 | **删除** |
| 风险 R2 本机→云端数据同步 | **删除**（这正好避免了再挖一条双写路径） |

**新增/强化的需求**

| 新需求 | 原因 |
|---|---|
| FR-COL-9 任务补跑 | 本机不常开，错过的抓取需要补 |
| FR-PUSH-5 推送补跑 | 同上，日报不能因为关机就永久丢失 |
| NFR-R4 漏执行可恢复 | 把"不保证开机"变成"保证补齐" |
| FR-OPS-9 开机自启 | 降低忘记启动的概率 |

**关键设计结论：把「不常开机」从缺陷转成可接受约束**

本地部署唯一真正的痛点是**定时任务可能漏跑**。解决方案不是要求你天天开机，而是：

1. 所有定时任务写入**执行记录表**（哪天该跑、是否跑过）
2. 应用启动时检查记录，**自动补跑**错过的抓取与推送
3. 结果：无论你隔几天开一次电脑，数据总是完整的，日报会补发

这条设计同时消除了 v1.1 中"必须上云"的理由。

### 11.3 移动端：明确不做（v1.3 变更）

**不做移动端界面**（不做 App、不做局域网网页版、不做 PWA）。
原 FR-UI-7 已移除，NFR-S5 相应简化为"仅监听 127.0.0.1，不开放局域网"。

**边界说明**：Telegram 机器人**保留**，但它的定位是**推送通道 + 群内快捷查询**，
不是"我们做的移动端界面"——它运行在 Telegram 客户端里，本项目没有任何移动端开发成本。
这两件事不矛盾：去掉的是"自己造移动端"，保留的是"借用现成通道"。

**影响**：v0.5 版本去掉局域网访问；服务边界收敛为本机浏览器 + Telegram 推送。
