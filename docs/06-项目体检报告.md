| | |

**纯占 1.5 GB 磁盘。** 删除即可，无风险。

### A2. 三个接口明显偏慢（实测）

| 接口 | 耗时 | 问题 |
|---|---|---|
| `/api/facets` | **784 ms** | 每次打开页面、每次同步完都跑 |
| `/api/semantic/status` | **280 ms** | **被顶部进度条每 2.5 秒轮询一次** |
| 按分类筛选 | 300 ms | 走临时排序 |
| 深翻页 page=50 | 333 ms | 同上 |

**根因（已用 EXPLAIN QUERY PLAN 确认）：**

```
facets 分类计数   → SCAN posts + USE TEMP B-TREE FOR GROUP BY   ← 全表扫描
浏览首页          → SEARCH USING idx_posts_isrep + TEMP B-TREE  ← 命中索引后还要临时排序
embedStats        → SCAN p                                      ← 全表扫描
```

现有索引只有 4 个：`(channel,msg_id)` `(cluster_key)` `(rep_id)` `(is_rep)`。
**缺 `(is_rep, ts)` 和 `(is_rep, category, ts)` 这类复合索引**，所以排序只能落临时表。
另外 `semantic/status` 里的「可索引条数」是每次现算全表 COUNT —— 它只在新帖入库时变，
**缓存即可**，280ms 能降到 ~1ms。

> 实测参考：带关键词的检索只要 **16 ms**（FTS 索引生效）。
> 也就是说「无关键词浏览」反而比「搜索」慢 14 倍，这个倒挂不该存在。
