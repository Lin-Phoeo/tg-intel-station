## 2. 设计目标与原则

| 编号 | 原则 | 说明 |
|---|---|---|
| G1 | **单一真相（Single Source of Truth）** | 数据只有一处权威副本，消除 D1 报告漂移 |
| G2 | **关注点分离** | 领域逻辑与 IO 解耦，便于单测 |
| G3 | **可测试优先** | 核心逻辑必须有纯函数边界，不依赖网络与磁盘 |
| G4 | **无原生依赖** | 不引入需编译的原生模块（NFR-C3），降低安装门槛 |
| G5 | **本地优先、零运维** | 双击即用；不引入数据库服务、消息队列、容器等外部依赖 |
| G6 | **渐进式演进** | 在现有可用系统上重构，不做推倒重写 |
| G7 | **失败可恢复** | 抓取可续跑、任务可补跑、数据可重建 |

```

│  表现层  Presentation                                        │
│  React 19 SPA（信息流 / 详情 / AI 助手 / 设置 / 来源管理）      │
└───────────────────────────┬─────────────────────────────────┘

┌───────────────────────────▼─────────────────────────────────┐
│  服务层  Service                                             │
│  index.mjs：REST 路由 / 静态资源 / SSE                        │
│  scheduler：定时任务与补跑                                     │
└───────┬─────────────────────────────┬───────────────────────┘
        │                             │
┌───────▼──────────────┐   ┌──────────▼───────────────────────┐
│  领域层  Domain        │   │  集成层  Integration              │
│  retrieve / rank      │   │  ai.mjs（LLM 与 RAG）             │
│  classify / score     │   │  bot.mjs（Telegram Bot API）      │
│  cluster（去重聚合）   │   │  fetcher（t.me / 网页抓取）       │
└───────┬──────────────┘   └──────────┬───────────────────────┘
        │                             │
┌───────▼─────────────────────────────▼───────────────────────┐
│  存储层  Storage                                             │
│  store.mjs：唯一写入口 insertPost()                            │

```

**关键约束**：任何模块想要写入数据，**只能**调用 `store.insertPost()`。这是消除 D1 的架构保证。

### 3.2 数据流（重构后）

```
data/raw/<频道>/seg_*.jsonl          ← 原始抓取，灾难恢复源，永久保留
        │
        ├──(首次建库 / 全量重建)──┐
        │                          │
增量抓取 source.mjs ──────────────┤
定时任务 scheduler ───────────────┼──► store.insertPost() ──► intel.db  ★唯一真相★
Telegram 机器人 bot.mjs ──────────┘            │
                                               ├──► 检索 API ──► UI
                                               ├──► RAG ──► AI 问答
                                               ├──► 报告生成（MD / CSV / XLSX）
                                               └──► 导出 clean.jsonl（归档/可移植）
```

与现状的差别：`clean.jsonl` 从"报告的数据源"降级为"DB 的导出产物"，
写入路径从两条收敛为一条。

## 6. 关键流程

### 6.1 采集入库（幂等）

```
ingest.run(source):
  1. 解析来源类型（core/parse）
  2. 拉取页面，解析出消息数组
  3. 对每条：core/classify 打标 → store.insertPost()
     └─ insertPost 内部按 (channel, msg_id) 判重，重复直接返回 duplicate
  4. 更新 sources.last_sync 与 imported 计数
  5. 写 job_runs（若为定时任务）
```

幂等保证：重复执行同一来源不会产生重复数据（NFR-R2）。

### 6.2 检索（分流 + 加权）

```
search(q, filters, sort):
  1. core/query 把查询串分词，按长度分流：
     ├─ 含 ≥3 字词 → 走 FTS5 trigram MATCH（主路径，当前 29 ms）
     ├─ 仅 2 字词   → v0.4 方案见 ADR-4；当前退化为 LIKE（926 ms）
     └─ 短词需与长词共存时 → FTS 做主过滤 + LIKE 做二次校验
  2. 附加筛选条件（分类/标签/频道/时间/分值）
  3. 排序：
     relevance → (bm25 - value * 0.5)
     date / value / views → 直接排序
  4. v0.4：向量重排 top-N（见 ADR-5）
```

### 6.3 定时任务与补跑（核心设计）

```
应用启动：
  scheduler.reconcile()
    for job in [daily_ingest(每天09:00), daily_digest(每天09:30), keyword_push(每小时)]:
      if !job_runs.exists(job, today) and now >= job.due:
          run(job)              ← 补跑错过的任务
运行中：
  setInterval(5 分钟):
      同上检查（幂等，已跑过的不会重复）
执行：
  run(job):
      job_runs.upsert(job, today, 'running')
      ... 执行 ...
      job_runs.upsert(job, today, 'done' | 'failed')
```

**这是本地部署方案成立的关键**：无论你隔几天开一次电脑，当天该跑的任务都会补上，
数据不丢、日报补发（对应 FR-COL-9 / FR-PUSH-5 / NFR-R4）。

### 6.4 AI 问答（RAG）

```
POST /api/chat
  1. ai.retrieve(question, filters, topK)
     ├─ 整句检索（权重 1.4）
     ├─ 分词检索（权重 1.0）
     ├─ 中文片段检索（权重 0.8）
     └─ 加权：价值分、时效、免费/限时标签、风险惩罚
  2. 推送 sources 事件（前端立即显示可点击来源）
  3. ai.buildMessages() 组装提示词
  4. streamLLM() 流式调用，SSE 逐块下发
  5. 无 API Key 时退化为「检索原文」模式
```

## 8. 设计决策记录（ADR）

### ADR-1 · 以 DB 作为唯一真相，JSONL 降级为导出格式 ★

- **问题**：现状 DB 与 `clean.jsonl` 两条可写路径，导致报告静默过期（D1）
- **决策**：`store.insertPost()` 作为唯一写入口；`clean.jsonl` 改为 DB 的导出产物；报告改为读 DB 生成
- **理由**：从架构上杜绝双写，而非靠约定；导出仍保留可移植性与灾难恢复能力
- **代价**：需重构 `build.mjs` / `report.mjs`；`data/raw` 必须继续保留
- **影响需求**：FR-OPS-5、D1、D6

### ADR-2 · 抽出 `core/` 领域层

- **问题**：`scrape/*.mjs` 被服务端反向引用（`../../scrape/...`），层级混乱，且批处理与在线路径各写一份
- **决策**：将解析、分类、查询构造、排序抽为无 IO 纯函数模块 `core/`
- **理由**：纯函数可单测（服务 G3）；两条路径复用同一实现，行为一致
- **代价**：一次性搬迁与引用调整
- **影响需求**：FR-OPS-3、NFR-M3

### ADR-3 · 定时任务用「执行记录 + 启动补跑」，不用系统计划任务

- **问题**：本地电脑不常开，定时任务会漏执行（D7）
- **决策**：应用内调度 + `job_runs` 记录 + 启动/周期 reconcile 补跑
- **备选**：Windows 任务计划程序 —— **否决**，理由：跨平台性差、逻辑割裂在系统外、无法感知业务状态
- **代价**：需要任务定义与幂等保证
- **影响需求**：FR-COL-9、FR-PUSH-5、NFR-R4

### ADR-4 · 2 字检索加速：**待原型验证**（不预先承诺方案）

- **问题**：`免费`/`开源`/`节点` 等 2 字词是最常用查询，却走 LIKE 全表扫（926 ms）
- **候选方案**：

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| A | **单字分词 + 短语查询**：把文本按字空格化存入 FTS，2 字查询变短语 `"免 费"` | 单索引同时支持 1/2/3+ 字；索引可能比 trigram 更小 | 需实测索引体积与短语查询性能 |
| B | 二元组影子列：额外存 bigram 并建第二索引 | 专治 2 字，命中率高 | 索引显著增大（估 +1 GB 级） |
| C | 保持 LIKE，加热点缓存 | 改动最小 | 治标不治本，冷查询仍慢 |

- **决策**：v0.4 先在 10 万条子集上做 A 的可行性实验（测索引体积、查询延迟、写入开销），再定方案
- **理由**：这是唯一一个**我无法靠推理确定**的设计点 —— 索引体积与 FTS 短语性能强依赖真实数据，必须实测
- **影响需求**：FR-SRCH-2、NFR-P2

### ADR-5 · 语义检索采用「FTS 粗排 + 向量精排」的混合模式

- **问题**：全量 85 万条做向量检索，float32 × 512 维约需 1.7 GB 内存，超出 NFR-P5
- **决策**：
  1. 只对 `value >= 4`（约 12 万条）生成 embedding，int8 量化后约 60 MB
  2. 查询时先由 FTS 召回 top 2000，再在这 2000 条内做余弦精排
- **理由**：内存可控；精排计算量从「12 万 × 512」降到「2000 × 512」，几十毫秒级；且召回质量由 FTS 兜底
- **备选**：引入 `sqlite-vec` 原生扩展 —— **否决**，违反 NFR-C3（无原生依赖）
- **影响需求**：FR-SRCH-5、NFR-P6

### ADR-6 · 不引入前端路由与状态管理库

- **问题**：是否需要 React Router / Redux
- **决策**：不引入。使用 URL 查询参数同步状态（已实现 `?q=&cat=&post=&theme=`）
- **理由**：单页多面板结构，状态简单；引入后增加体积与学习成本，收益低；现有 URL 参数已满足分享与刷新恢复
- **影响需求**：FR-UI-6、NFR-P3

### ADR-7 · 测试策略：`node:test` 单元测试 + 构建作为 CI 门禁

- **决策**：
  - 单元测试覆盖 `core/*`（纯函数，最易测也最易碎）
  - 集成测试：在临时 DB 上跑「导入 → 检索」闭环
  - 前端暂不引入 Vitest，以 `vite build` 通过作为门禁
- **理由**：Node 内置测试运行器，零新增依赖（符合 G4）；优先覆盖回归风险最高的逻辑
- **影响需求**：FR-OPS-3/4、NFR-M1/M2

### ADR-8 · 备份采用「DB 文件 + 配置」打包，而非导出 SQL

- **决策**：备份 = 停写 → 复制 `intel.db` + `settings.json` + `bot.json` → 打包 zip
- **理由**：SQLite 单文件天然适合快照；导出 SQL 会丢失 FTS 索引，恢复慢
- **代价**：备份文件较大（约 1.5 GB）
- **影响需求**：FR-OPS-6

### ADR-9 · 报告生成保留，但降级为「按需触发」

- **问题**：688 MB 产物中包含 577 MB 现已过期的 CSV/XLSX
- **决策**：报告不再随每次采集自动全量重生成；改为按需触发（应用内按钮 / 命令），且从 DB 生成
- **理由**：报告是「快照」而非「主界面」，主界面是应用本身；避免无谓的磁盘与时间开销
- **影响需求**：FR-OPS-2、D6
